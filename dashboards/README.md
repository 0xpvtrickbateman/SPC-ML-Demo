## Import and verify in Databricks

1. In Catalog Explorer, open `ml_statistical_process_controls → demo_schema`. Confirm this is the authorized demo destination and that your notebook identity can write there. This catalog uses **default storage, which requires serverless compute for direct access**. For this catalog, use serverless notebook compute and a serverless SQL warehouse; verify their availability and your permissions. This is a constraint of this selected catalog, not a statement about all Databricks catalogs.
2. Open the repository as a Git folder so `notebooks/model_reuse.py` sits beside both notebooks. For a manual import, import `notebooks/SPC_ML_Demo.py` and `notebooks/SPC_Model_Scoring.py`, and upload `model_reuse.py` to the same folder as a workspace file, not a notebook. Preserve any existing notebook you need. Keep the default `OUTPUT_SCHEMA = "ml_statistical_process_controls.demo_schema"`. Keep `UC_MODEL_NAME` empty unless intentionally registering a candidate.
3. In both notebooks' Environment panels, choose the same environment version and dependencies. The Standard serverless base lacks statsmodels: add `-r /Workspace/<your folder>/requirements-demo-lock.txt` to reproduce the recorded results, or at minimum `statsmodels==0.14.6`. Attach serverless Python notebook compute and run all cells. A SQL warehouse cannot execute the Python notebook. Confirm Cell 19 printed `Saved forecast bundle`, check the output table manifest and every write result, and do not infer success from the dashboard file.
4. Refresh Catalog Explorer. Confirm `demo_drift_inputs` has 54 rows, `demo_drift_performance` 18, and `demo_drift_daily` 450 for `dataset_id = 'attainx_applications_v3_seed42'`; also inspect `review_queue`. Rerunning the same seed must preserve unique table keys. Use the manifest for the full table list.
5. Import `AttainX_SPC_Demo.lvdash.json` through Dashboards → Import dashboard from file. You may use the checked-in file directly or download it from `setup.html`; both default to the same destination.
6. Select an accessible serverless SQL warehouse for this catalog. Open the Data tab and run all ten datasets. Verify read permissions, schema compatibility and results before inspecting Canvas.
7. Inspect Overview, Detect drift, Drift exercise and Review and retrain. Confirm the Intake A default filter, switch queues, then clear the filter. Check model identity, execution timestamp, historical data dates, charts, review statuses and table columns. Publishing is a separate sharing choice; a draft supports rehearsal.

If you choose another authorized schema, update the notebook setting and both helper fields together. `TABLE_OR_VIEW_NOT_FOUND` requires checking the destination and notebook write results. Permission errors require the appropriate catalog/schema/table grants for the notebook and warehouse identities. Existing tables from an older schema may require migration; local tests cannot certify those tables.

## Four-part walkthrough

| View | Question | Evidence |
| --- | --- | --- |
| Overview | Are forecasts useful? | Synthetic application-volume story; 1,179,830 events aggregated to 1,260 daily observations; actuals, saved one-day predictions, simple baseline, latest MAE, coverage and model identity |
| Detect drift | What changed? | Three input distributions versus training; prediction error over three separate 25-business-day windows; comparison dates, invalid or missing rates and finite sample counts |
| Drift exercise | Can the warning fire? | Separate +350-application outcome scenario with frozen predictions; a one-window watch followed by a two-window review |
| Review and retrain | What happens next? | Investigate data and process changes; train a candidate; validate on later dates; obtain human approval; retain rollback; inspect the separate SPC queue |

Intake A and Intake B count application receipts. Completions A counts workflow completion events. These are independent synthetic streams, not linked case histories or actual USCIS performance measurements. Models train on daily windows, not a million independent examples.

The native dashboard and companion both have four content views. The companion also has an evidence dropdown; the native replay and exercise pages have fixed scenarios. Clearing the native queue filter sums daily counts across queues while preserving queue identity in error curves and tables. The SPC queue always represents recorded replay, never exercise outcomes.

## Definitions and boundaries

Input change is Wasserstein distance divided by training standard deviation for `last_value`, `window_std` and `trend`. Scores above 0.5 prompt investigation. Fewer than 20 finite samples or insufficient reference variation produce unavailable evidence. The evidence counts include only finite values. The existing `missing_rate` column is displayed as **Invalid or missing rate**: the fraction of the window's expected business days, from the configured calendar, whose input is absent, NaN, positive infinity or negative infinity. These same finite masks determine the score and its sample eligibility. This illustrative diagnostic is not a significance test or proof of concept drift.

Performance monitoring uses a frozen one-day random forest and 75 held-out dates split into three 25-day windows. Window 0 establishes each queue’s reference MAE. Two consecutive monitoring windows above `1.25 × max(reference MAE, 1 count)`, with at least 20 matched actuals in each window and reference, trigger **Review for retraining**. Windows follow the configured business calendar; expected actuals and coverage count every business day, so absent days lower coverage instead of shifting windows. Insufficient actuals are not evidence of healthy performance. Bias is **forecast − actual**, so positive bias means **overprediction**.

The controlled exercise adds **350** to evaluation outcomes after the reference window. Inputs, saved predictions, original counts, original model metrics and SPC reviews remain unchanged. Both model and simple-baseline predictions stay frozen. This tests the warning rule, not causality. No alert automatically authorizes retraining or promotion.

Model identity is an actual MLflow URI when available or an explicitly local artifact hash. `run_generated_at` records execution time; the training, reference and current-window dates describe historical evidence. The replay ends September 8, 2026. Refreshing the native dashboard reads saved tables. Running the demonstration notebook retrains its demonstration models; the separate scoring notebook loads saved models. Production monitoring still needs independent new-data ingestion, durable prediction/actual joins, calibrated thresholds and approvals.

## Rebuild and verify locally

From the repository root:

```bash
.venv/bin/python scripts/build_dashboard.py --preview
.venv/bin/python -m pip install duckdb==1.4.4
.venv/bin/python tests/drift_input_evidence_test.py
.venv/bin/python tests/dashboard_test.py
node tests/setup_helper_test.mjs
```

`--preview` enables the notebook’s local-test mode and regenerates the companion and data snapshot without external writes. Omit it to rebuild only native JSON and setup HTML. `--schema authorized_catalog.authorized_schema` binds the native JSON to an alternate destination. The helper remains prefilled with the default destination and allows its fields to be changed independently; download from its displayed destination.

Tests verify drift math and missing-data boundaries, scenario isolation, frozen predictions, three simulated Delta merges, all ten native dataset queries and eleven example SQL statements in DuckDB, complete filter bindings, field encodings and nonoverlapping layouts. The helper test verifies defaults, alternate destinations and invalid-name rejection. These checks do not certify Databricks import, Spark execution, serverless availability, permissions or native widget rendering. Complete the workspace checks above for cloud acceptance.
